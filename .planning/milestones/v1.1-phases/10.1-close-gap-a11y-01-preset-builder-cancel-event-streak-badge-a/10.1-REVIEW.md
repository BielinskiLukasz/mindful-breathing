## Summary

Reviewed `index.html` for the three targeted fixes in phase 10.1:

1. **Fix 1** — `cancel` event listener on `presetBuilderDialog` (Escape key path): correctly sets state and delegates to `closeSettings()`. No double-close risk; the keyboard handler does not intercept `openPanelElement === presetBuilderDialog` so the browser fires the native `cancel` event unimpeded, and calling `dialog.close()` programmatically (in the other handlers) does not re-fire `cancel`. Event routing is sound.

2. **Fix 2** — Streak update calls added to `importJson()` and `importCsv()` after `renderHistory()`. Call order matches the established pattern used in `finishSession()` and `reset()` (badge → panel → maybeUpdateLongest). `maybeUpdateLongestStreak()` calls `saveSettings()` internally when the streak improves; no double-save concern since neither import function calls `saveSettings()` itself. Correct.

3. **Fix 3** — Four `openPanelElement = null` assignments replaced with `closeSettings()`. The settings overlay was previously left open (visible) while `openPanelElement` was nulled, breaking the Tab focus trap and unblocking Space/R/F shortcuts. Replacement is correct in intent. However one of the four call sites carries a dead focus call that masks the intended return path (WR-01), and `closeSettings()` has an unconditional focus side-effect that is latently unsafe (WR-02).

No correctness bugs or security issues were found. Both warnings are maintainability/accessibility concerns that should be addressed before further handlers are added near this code path.

## Warnings

### WR-01: Dead `newPresetBtn.focus()` call in `cancel` event handler

**File:** `index.html:2067`
**Issue:** `closeSettings()` is called on line 2066, which removes the `.visible` class from `settingsOverlay` (`display: none` is restored). `newPresetBtn` is a child of `settingsOverlay` (line 1416, inside `.settingsPanel > .settingsGroup > #presets`). Browsers silently ignore `.focus()` calls on any element whose ancestor has `display: none`, so the call on line 2067 is always a no-op. Focus correctly ends up on `settingsBtn` from `closeSettings()`. The dead call is never reachable with the intended effect, creates a misleading intent signal, and diverges from the identical `presetCancelBtn.click` handler (line 2122–2130) which has no post-`closeSettings()` focus override.

**Fix:** Remove line 2067.
```javascript
// BEFORE
closeSettings();
document.getElementById("newPresetBtn")?.focus();   // always no-op: parent is display:none

// AFTER
closeSettings();   // already routes focus to settingsBtn — no further call needed
```

### WR-02: `closeSettings()` calls `settingsBtn.focus()` unconditionally — unsafe idempotency

**File:** `index.html:3520–3524`
**Issue:** `closeSettings()` always calls `settingsBtn.focus()` regardless of whether the settings overlay was open when called:
```javascript
function closeSettings() {
  settingsOverlay.classList.remove("visible");
  openPanelElement = null;
  settingsBtn.focus();          // fires even if settings was already closed
}
```
All four current call sites in the preset builder handlers (lines 2066, 2129, 2205, 2256) are safe because the preset builder is only reachable from within the settings overlay. However, the function does not guard against being called when settings is closed. Any future handler that calls `closeSettings()` as a cleanup safety net (a reasonable assumption given the name) will unexpectedly steal focus to `settingsBtn`. This is the same pattern that caused the original `openPanelElement = null` regression that Fix 3 corrected.

**Fix:** Guard the focus call to only fire when settings was actually visible:
```javascript
function closeSettings() {
  const wasOpen = settingsOverlay.classList.contains("visible");
  settingsOverlay.classList.remove("visible");
  openPanelElement = null;
  if (wasOpen) settingsBtn.focus();
}
```

## Info

### IN-01: App startup omits `maybeUpdateLongestStreak()` after streak initialization

**File:** `index.html:3624–3626`
**Issue:** The startup sequence calls `renderHistory()`, `updateStreakBadge()`, `updateStreakPanel()` but not `maybeUpdateLongestStreak()`. The import functions (added in Fix 2) correctly call all four. If `longestStreak` in `localStorage` is stale or was manually removed, the computed streak from history can exceed the persisted `longestStreak` indefinitely until the next session finishes or a file import runs.

**Fix:** Add the call at startup, matching the import pattern:
```javascript
renderHistory();
updateStreakBadge();
updateStreakPanel();
maybeUpdateLongestStreak();   // add this line
```
