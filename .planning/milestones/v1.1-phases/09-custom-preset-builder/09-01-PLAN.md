<assumption_delta_decision>
**Assumption-Delta Architecture Checkpoint:**

Phase 09 introduces custom presets alongside three built-in presets — a singular→plural transition in the preset model. The existing code assumes `activePresetKey` is always a key in the frozen `PRESETS` object.

**Decision:** `add-alongside` — custom presets extend the preset model by adding a parallel lookup path (check `key in PRESETS` first, then check custom presets array when selecting a preset). This is accepted debt: if a third category were added, the lookup chain would need generalizing to a registry pattern. For Phase 09, custom preset IDs like `"custom-1722456789123"` are valid values for `activePresetKey`, but the lookup happens at the point of use (in the presetsEl click handler and in activePhases initialization), not globally.

**Implications:** Task 2 of Plan 02 (tracer) will need to extend the presetsEl click handler to check custom presets when the clicked key is not in PRESETS. Task 1 of Plan 02 (tracer) will need to build activePhases from custom preset phases, applying type→breathR/theme/cue lookup at runtime.
</assumption_delta_decision>
